# MLT Облік — фронтенд (прототип на мокових даних)

Внутрішня система сервісного центру для обліку закупівель, складських залишків і
вкладень у ремонти. Заявки надходять із RO App (тільки читання), собівартість рахує
MLT Облік.

Це **етап 1 за ТЗ**: клікабельний фронтенд без бекенда. Уся бізнес-логіка працює
в браузері на мокових даних, тож клієнт може пройти реальні сценарії.

## Запуск

```bash
npm install
npm run dev
```

Перевірка типів і зборка, лінтер і тести бізнес-логіки:

```bash
npm run build
npm run lint
npm test
```

На екрані входу є швидкий вхід за трьох демо-користувачів:

| Користувач | Роль | Особливість |
|---|---|---|
| Роман Марценюк | Адміністратор | повний набір прав |
| Андрій Коваль | Виконавець | заявки, склад, закупівлі |
| Оксана Лисенко | Виконавець | + індивідуальні менеджерські права |

Пароль не перевіряється. Перемикач користувача є також у шапці.

## Стек

React 19, Vite, TypeScript, Tailwind CSS v4 (через `@tailwindcss/postcss`),
React Router v7, Recharts, TanStack Query (кеш і стани завантаження), Vitest
(тести бізнес-логіки). Аліас `@/*` вказує на `src/*`.

Примітиви інтерфейсу (діалог, меню, таби, перемикачі, тости) написані вручну
в `src/components/ui` у стилі shadcn/ui, без Radix — так немає конфліктів
peer-залежностей з React 19 і Vite 8. За потреби їх можна замінити на компоненти
з shadcn CLI: API та класи збігаються.

## Дизайн-система

Нейтральна база shadcn/ui. Кольори — **тільки через CSS-токени** в `src/index.css`,
жодних hex у компонентах. Світла й темна теми, перемикач у шапці.

Масштаб типографіки, відступи й радіуси збігаються зі стандартними значеннями
Tailwind, тому окремих токенів для них не вводили:

- `text-4xl` 36/40 (h1), `text-3xl` 30/36 (h2), `text-2xl` 24/32 (h3),
  `text-base` 16/24 (body), `text-sm` 14/20 (small), `text-xs` 12/16 (caption)
- відступи 1 / 2 / 4 / 6 = 4 / 8 / 16 / 24 px
- `rounded-sm` / `rounded-md` / `rounded-lg` = 4 / 6 / 8 px

Поверх восьми базових токенів додано рівно два — `success` і `warning`, лише для
бейджів статусів. Статуси завжди читаються без кольору: бейдж має підпис та іконку.
Графіки використовують нейтральний рамп `--chart-1…5`, похідний від базової палітри.

Контраст основного тексту й `muted-foreground` на фоні, а також тексту на
`success` і `warning` — не менше 4.5:1 в обох темах.

## Структура

```
src/
  api/                   єдиний шар доступу до даних
    contract/            контракт: типи, DTO, інтерфейс ApiClient, ApiResult
    hooks/               хуки TanStack Query (читання й запис, інвалідація кешу)
    active-client.ts     ЄДИНА точка заміни мока на справжній сервер
    mock/                уся імітація сервера (замінюється цілком)
      storage.ts         база в localStorage
      handlers/          реалізація ApiClient по модулях
      engine/            бізнес-логіка + тести (піде на сервер майже без змін)
      seed/              демо-дані, розбиті за сутностями
  store/                 ui-store (тема, мобільний режим, тости)
  lib/                   форматування, підписи enum, період, утиліти
  components/            ui (примітиви), common, layout, allocation, inventory,
                         purchases, orders, users, integration
  pages/                 16 сторінок
```

Сторінки й компоненти працюють з даними **лише через `@/api`**: імпорт
`@/api/mock/*` ззовні `src/api` заборонений правилом ESLint. Бізнес-логіка живе
в `src/api/mock/engine` окремо від компонентів — її можна перенести в NestJS
майже без змін разом з тестами. Щоб підключити справжній бекенд, достатньо
написати HTTP-реалізацію `ApiClient` і експортувати її з `api/active-client.ts`.

## Реалізовані правила

- **Закупівля ≠ витрата.** Суми закупівель і вкладень не додаються: частина грошей
  лежить на складі, частина вже розподілена по ремонтах.
- **FIFO.** Ціна вкладення рахується автоматично з партій, найстаріші першими. Якщо
  кількість перекриває кілька партій, створюється кілька рядків списання, кожен зі
  своєю ціною. Вручну ціна вводиться лише при створенні закупівлі.
- **Миттєва синхронізація складу.** Вкладення одразу зменшує залишок; повернення або
  скасування повертає кількість і вартість саме в ті партії, з яких були взяті.
- **Нульовий залишок не ховає товар** — позиція лишається з позначкою
  «Немає в наявності» і поповнюється новою закупівлею.
- **Відʼємні залишки заборонені без винятків.** Ручне коригування вимагає причини
  і запису в журнал, але теж не може вивести залишок нижче нуля.
- **Партії за різними цінами.** Історична собівартість не змінюється, коли приходить
  нова партія дорожче або дешевше.
- **Два призначення закупівлі:** на склад або напряму в заявку. У другому випадку
  позиція в залишок складу не потрапляє.
- **Перенесення та повернення** не створюють повторних витрат і не збільшують
  загальну суму закупівель.
- **Закриті заявки.** Заявка закрита лише в статусі «Видано» (статус «Готово» її не
  блокує, а статуси приходять тільки з RO App). Змінювати вкладення закритої заявки
  може лише користувач із правом `allocations.edit_closed`, причина обовʼязкова,
  усе йде в журнал.
- **Фінансові записи не видаляються** — тільки скасування, сторно або коригування.
- **Прослідковуваність.** Кожне число на головній і в аналітиці веде до своїх
  операцій, закупівель і заявок.

## Інтеграція з RO App (симуляція)

На сторінці «Інтеграція RO App» показані три способи оновлення даних:
вебхуки, глобальне оновлення по кнопці та нічний автозапуск. Усі три йдуть через
одну логіку й пишуть події в журнал синхронізації з позначкою джерела. Є приклад
невдалої синхронізації та банер про роботу на вже завантажених даних.

Статуси й типи заявок читаються з довідників RO App і мапляться в локальні enum.
Незмаплене значення показується як є і нічого не ламає — приклад є у заявці № 4215
зі статусом `on-hold`.

Назад у RO App нічого не записується.

## Мобільний режим

Для майстрів — рівно два розділи в нижній навігації: **Заявки** і
**Склад і закупівлі**. Великі зони дотику, картки замість таблиць, повноекранні
листи замість діалогів, нативний вибір у списках.

Щоб показати мобільний вигляд з ноутбука, у шапці є перемикач — застосунок
відкривається в рамці телефона шириною 390 px.

## Чого немає у першій версії

Бекенд і справжні запити до API, запис у RO App, інтерфейс додаткових витрат
(у даних закладено сутність `Expense` і тип категорії «Витрата»), маржа та прибуток,
роль бухгалтера й власника, офлайн-режим, установка PWA, зміна статусів заявок.

## Демо-дані

Стан зберігається в `localStorage`. Кнопка «Скинути демо-дані» в налаштуваннях
повертає початковий набір: 16 заявок, 18 товарів, 11 закупівель, 29 вкладень,
партії за різними цінами, залишки на складі та скасована закупівля.
