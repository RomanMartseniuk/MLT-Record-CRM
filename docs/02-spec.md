### Границы версии 1

**Входит:** заявки с клиентом и техникой, склад с партиями, закупки (на склад; напрямую в заявку только из карточки заявки), вложения в заявки, пользователи и права, dashboard и аналитика себестоимости, журнал операций, мобильный режим из двух разделов.

**Не входит:** запись данных в RO App, дополнительные расходы (только фундамент), маржа и прибыль, офлайн-режим, управление ремонтами, клиентская CRM.

## 1. Введение и цели проекта

- **Назначение:** сервисный центр использует RO App для заявок, но не может удобно вести учёт затрат на каждую заявку. MLT Облік подтягивает заявки по API и ведёт собственный учёт закупок, склада и вложений.
- **Результат:** достоверная себестоимость каждого ремонта и прозрачное движение денег и запчастей. Любая сумма прослеживается до операции, закупки, позиции или заявки.
- **Архитектура:** единое приложение, единый API, единая база. Модульный монолит без микросервисов. Должна оставаться расширяемой: новые типы расходов, склады, отчёты, интеграции.

## 2. Глоссарий

- **Товар** — позиция номенклатуры (например, «Карбюратор Honda Dio»).
- **Партия** — поступление товара с конкретной ценой и количеством.
- **Закупка** — документ с одной или несколькими позициями.
- **Вложение** — привязка товара из партии к заявке (в коде — Allocation).
- **Заявка** — ремонт из RO App.
- **Нераспределённый товар = товар на складе.** Это одно и то же понятие. Остаток партии, не вложенный в заявки, и есть складской остаток. Отдельной цены или суммы «нераспределённого» нет: есть одна стоимость остатка (остаток × цена партии).

Основные сущности БД: User, Role, Permission, Order, Client, Asset, Supplier, Category (с типом), Product (с фото и ссылками), Purchase, PurchaseItem, Batch, InventoryMovement, Allocation, AllocationMovement, Expense (заготовка), Attachment, AuditLog, IntegrationLog, SystemSetting.

## 3. Роли и права

В MVP две роли:

- **Администратор** — полный набор прав.
- **Исполнитель (мастер)** — рабочий интерфейс заявок, склада и закупок.

Менеджер отдельной ролью не является: администратор выдаёт менеджерские права каждому пользователю индивидуально через разрешения. Роли владельца и бухгалтера в MVP не нужны, но схема прав позволяет добавить их позже.

Примеры разрешений: `purchases.view`, `purchases.create`, `allocations.create`, `allocations.edit_closed`, `inventory.manage`, `reports.view`, `reports.export`, `users.manage`, `settings.manage`. Проверка только на сервере.

- Правка вложений в закрытой заявке требует права `allocations.edit_closed`. Закрытой считается только заявка в статусе «Выдан» (локальный `closed`, «Видано»); «Готово» заявку не блокирует. По умолчанию право только у администратора. Причина изменения обязательна. Статусы приходят только из RO App, система их не меняет.
- Мастер не может менять чужие финансовые операции и системные настройки.
- Пользователей создаёт администратор, самостоятельной регистрации нет.
- Пользователь MLT может быть связан с сотрудником RO App (менеджер, исполнитель).

## 4. Функциональные требования

### 4.1. Склад и партии

- Товар хранит: название, категорию, единицу измерения, фото, несколько ссылок на магазины (подпись и URL), текущий остаток, среднюю цену, стоимость остатка.
- Дробное количество поддерживается (литры масла и т. п.).
- Поступление по разным ценам образует разные партии. Цены партий хранятся отдельно, историческая стоимость не пересчитывается по текущей цене.
- Нулевой остаток не удаляет товар: он остаётся в списке со статусом «немає в наявності» и пополняется новой закупкой. Фильтр позволяет показать только товары в наличии.
- Физическое наличие, резерв и распределённое количество учитываются раздельно.
- Отрицательные остатки запрещены без исключений. Ручная корректировка требует обязательной причины и записи в журнал, но тоже не может увести остаток ниже нуля.

### 4.2. Закупки

- Закупка содержит дату, поставщика, номер чека или накладной, комментарий, фото чека и несколько позиций. Сумма считается автоматически.
- Два назначения закупки (выбор назначения есть не на странице «Нова закупівля», см. ниже):
  - **на склад** — партии поступают на склад, в заявки ничего не распределяется. Это значение по умолчанию: закупка, созданная на странице «Закупівлі → Нова закупівля», всегда идёт на склад;
  - **напрямую в заявку** — создаётся только из диалога добавления вложения внутри карточки заявки: вложение создаётся сразу, в остаток склада позиция не попадает.
- Закупку можно создать прямо из заявки, включая создание нового товара. Только такая закупка получает назначение «в заявку».
- Статусы закупки вычисляются: новая, частично распределена, полностью распределена, отменена.
- Закупка не удаляется физически, только отменяется. Справочник поставщиков с деактивацией, история закупок поставщика сохраняется.

### 4.3. Вложения в заявки

- В карточке заявки кнопка «Додати вкладення». Умный поиск по складу показывает остаток, количество вводится вручную.
- Если товар не найден, предлагается создать товар и оформить закупку: «Нічого не знайдено. Створити новий продукт на складі і оформити закупівлю?».
- Цена определяется автоматически по FIFO из партий. Если количество охватывает несколько партий, создаётся несколько записей списания.
- Вложение мгновенно уменьшает остаток. Удаление из заявки возвращает количество и стоимость в исходные партии.
- Частичное распределение, распределение одной закупки на несколько заявок, перенос между заявками, возврат на склад, отмена ошибочного вложения.
- Каждое действие — отдельная учётная операция. Перенос не увеличивает сумму закупок.
- **Вложение-услуга.** Кроме товара со склада, в заявку можно вложить услугу или работу (например, «Перемотка альтернатора»: сервис отправил деталь на перемотку специалистам). Услуга вводится только в диалоге вложения внутри карточки заявки: название вручную (справочника услуг нет), сумма вручную, комментарий. Услуга не связана со складом, закупками и партиями, FIFO к ней не применяется, остатки не меняются. Подрядчика у услуги нет. Переносить услугу в другую заявку нельзя, только отменить. Название, сумму и комментарий можно править, причина необязательна (в закрытой заявке обязательна, как у товара). Стоимость услуги входит в себестоимость заявки так же, как стоимость товарных вложений. Правила закрытых заявок, причины и журнал операций действуют для услуг так же.

### 4.4. Финансовые правила

- Закупка и вложение — разные события. Показатели не суммируются как независимые расходы (нет двойного учёта).
- Различать: закупки, остатки, вложения, возвраты, списания, корректировки.
- Себестоимость заявки = сумма её вложений (товарных и услуг) на момент операций.
- Финансовые записи не удаляются: только отмена, сторно или корректировка.
- Операции со складом и деньгами атомарны (транзакция PostgreSQL) и защищены от повторной отправки (idempotency key).

### 4.5. Аналитика и dashboard

**Dashboard:** общая сумма закупок, вложения в ремонты, стоимость остатков на складе (единая цифра, отдельной плитки «нераспределённые» нет), активные заявки с вложениями, последние операции, фильтр периода. Диаграмма делит закупки периода на «У заявках» и «На складі».

**Аналитика (только себестоимость):** средняя, минимальная и максимальная себестоимость; по типам техники, категориям, поставщикам, сотрудникам; динамика по периодам. Экспорт XLSX, CSV, PDF с учётом фильтров.

### 4.6. Журнал операций

Пользователь, тип операции, время, объект, старые и новые значения, причина. Фиксируются создание и изменение закупок, вложения, переносы, возвраты, корректировки, отмены, изменения справочников.

### 4.7. Распределение со склада (бывшая страница «Нераспределённые закупки»)

Отдельной страницы нет: нераспределённые позиции — это складские остатки (см. глоссарий). На странице «Склад» в строке каждого товара с остатком есть кнопка «Розподілити». Она открывает диалог: заявка (только не закрытые), количество, ориентировочная сумма. Цена определяется FIFO, выбирать конкретную партию не нужно. Детали партий (поставщик, дата, остаток) видны в карточке товара. По закупке остаётся показатель «Залишок на складі» (остаток её партий × цена партий).

Инвариант: сумма «Залишок на складі» по всем неотменённым закупкам плюс стоимость остатков партий-корректировок равна сумме «Вартість» по всем товарам склада. Ручная корректировка остатка не привязана к закупке: это отдельная операция «Коригування» в журнале, её партия (`adjustment`) не входит ни в одну закупку и учитывается в сверке отдельным слагаемым.

### 4.8. Фундамент для дополнительных расходов

Без UI в v1, но в схему закладывается:

- сущность Expense (сумма, категория, дата, автор, привязка к заявке, комментарий, файл);
- у категории тип: товар или услуга (`product | service`, решение разработчика; `service` пока задел);
- вложения и расходы заявки считаются через единый FinanceModule, чтобы себестоимость позже включила расходы без переписывания.

## 5. Пользовательский интерфейс

**Десктоп:** вход (JWT), dashboard, заявки и карточка заявки, закупки, склад (с распределением по заявкам), поставщики, категории, аналитика себестоимости, журнал операций, пользователи и настройки, состояние интеграции.

**Мобильный режим** (для мастеров), два раздела:

1. **Заявки** — быстрый поиск, карточка, добавление вложения.
2. **Склад и закупки** — форма закупки с фото чека, добавление товара, остатки с кнопкой «Розподілити».

Крупные элементы, минимум вложенных меню, PWA для iPhone (позже). Светлая и тёмная темы, по умолчанию тёмная. Весь текст интерфейса на украинском.

**Палитра (обязательна):** `#06141B`, `#11212D`, `#253745`, `#4A5C6A`, `#9BA8AB`, `#CCD0CF`. Цвета задаются только токенами в `client/src/index.css`, hex в компонентах не используется. Красный, зелёный и жёлтый вне палитры допустимы только для ошибок и статусов.

## 6. Интеграции и API (RO App)

- **Авторизация:** Bearer-токен RO App, хранится только на сервере, во фронтенд не попадает.
- **Обновление данных** идёт тремя способами:
  1. вебхуки RO App — изменения приходят в реальном времени;
  2. глобальное обновление по кнопке — ручной запуск полной синхронизации;
  3. автоматическое обновление раз в сутки ночью — страховка на случай пропущенных вебхуков.

  Плюс первичная загрузка при запуске. Все способы используют одну логику без дублей, события пишутся в IntegrationLog с указанием источника (вебхук, кнопка, ночной запуск). Вебхук-эндпоинт проверяет подпись или секрет запроса.
- **Идентификация:** заявка, клиент и техника определяются стабильным внешним ID, а не номером. Повторная синхронизация не создаёт дублей.
- **Справочники:** статусы и типы заявок загружаются из List Order Statuses и List Order Types и маппятся в локальные enum. Неизвестный статус отображается как есть.
- Даты в формате ISO 8601, пагинация через `pageSize`.
- При недоступности RO App система работает с загруженными данными. Ошибки интеграции не приводят к потере финансовых операций.
- Отдельная страница состояния интеграции: последняя успешная синхронизация, ошибки, кнопка ручной синхронизации.

## 7. Нефункциональные требования

- **Безопасность:** JWT, безопасное хранение паролей, серверная проверка прав, валидация входных данных (DTO), защита от SQL injection, ограничение доступа к файлам, безопасное хранение ключей RO App.
- **Надёжность:** регулярное резервное копирование PostgreSQL и проверка восстановления, журналирование критических действий.
- **Данные:** деньги в Decimal, а не Float; стоимость позиции сохраняется на момент операции.
- **API:** REST, пагинация, фильтрация, сортировка, централизованная обработка ошибок.
- **Платформы:** ноутбук и iPhone, адаптивный дизайн.

## Этапы

1. **Прототип** — кликабельный фронтенд на моках (React), согласование с клиентом.
2. **Фундамент** — проект, БД, JWT, роли и разрешения.
3. **Интеграция RO App** — заявки, клиенты, техника, справочники, вебхуки, синхронизация.
4. **Закупки и склад** — справочники, партии, закупки.
5. **Вложения** — FIFO, переносы, возвраты, правила закрытых заявок.
6. **Аналитика и отчёты.**
7. **Мобильный режим и PWA.**
8. **Финальная проверка** — финансовые расчёты, права, интеграция, резервное копирование.

## Критерии готовности

- [ ] Вход и доступ по ролям работают, права проверяются на сервере
- [ ] Заявки, клиенты и техника синхронизируются без дублей
- [ ] Закупку с несколькими позициями можно создать на склад (со страницы закупок) и напрямую в заявку (из карточки заявки)
- [ ] Вложение полностью или частично, цена по FIFO, остатки меняются мгновенно
- [ ] Удаление, перенос и возврат не создают повторных расходов
- [ ] Нулевой остаток не удаляет товар
- [ ] Закрытую заявку может править только уполномоченный пользователь, причина обязательна

- [ ] Dashboard и отчёты дают корректные суммы с переходом к операциям
- [ ] Критические действия попадают в журнал
- [ ] Система работает на ноутбуке и iPhone

- Закрытая заявка = только статус «Выдан» (раньше блокировали ещё и «Готово»). Право `allocations.edit_closed` остаётся у администратора (раздел 3).
- Ручная корректировка остатка остаётся отдельной операцией «Коригування» (не закупка). Сверка склада с закупками получила слагаемое «партии-корректировки» (раздел 4.7).
- Вложение-услуга (раздел 4.3): в заявку можно вложить услугу или работу с названием и суммой, введёнными вручную. В БД это та же сущность `Allocation` с необязательным `productId` и признаком вида (товар / услуга), без `AllocationLine`. Складу и закупкам не касается. Затрагивает клиент (`contract/types.ts`, диалог вложения, движок allocations) и серверную схему (слой 4).
- Тип категории: `product | service` (раньше `product | expense`). У `Supplier` поля `phone` и `email` могут содержать несколько значений.
- Схема БД (слои 1-5): номер закупки `З-00001` (минимум 5 цифр, дальше растёт без ограничения). Отмена закупки без причины (`cancelledAt`, `cancelledById`). Фото и файлы через `Attachment` (товар, чек, расход). Защита от повторной отправки через `IdempotencyKey`. Менеджер и исполнитель заявки хранятся именем и `roAppId`. Финансовые связи с `onDelete: Restrict`. Тип категории остаётся `product | service`, решение подтверждено.
- Рефакторинг клиента (спецификация и план в `docs/superpowers/`): страницы работают с данными только через слой `src/api` (контракт, хуки, `api/mock`), имитация сервера целиком лежит в `api/mock` и заменяется одним экспортом. Поведение для пользователя не менялось, кроме: журнал операций и «Останні операції» идут от новых к старым, диалог переноса вложения всегда показывает поле причины (обязательна, если одна из заявок закрыта), сравнение с предыдущим периодом в аналитике считается точно равной длины. Правила сверки склада проверяются автотестами движка.
