# Бэкенд: модули, инварианты, план

Бэкенд (`server/`, NestJS + Prisma + PostgreSQL) разработчик пишет сам. Этот документ — согласованный план. Не генерируйте модули целиком без запроса: объясняйте, предлагайте, проверяйте.

Источник бизнес-правил: `client/src/api/mock/engine/` (бывший `client/src/domain/`) с тестами `*.test.ts`. Он переносится на сервер почти без изменений, но с транзакциями, блокировками и серверной проверкой прав. Спецификацией эндпоинтов служит контракт `client/src/api/contract/` (`client.ts` и `dto/*`): каждый подинтерфейс `ApiClient` соответствует модулю ниже, а входы и ответы описаны там же.

## 1. Модули

| Модуль | Отвечает за | Зависит от |
|---|---|---|
| common | Prisma-сервис, конфиг, единый формат ошибок, пагинация, работа с деньгами, транзакции, idempotency key | — |
| auth | Логин, JWT (access + refresh), текущий пользователь | users |
| users | Пользователи, роли, индивидуальные права, блокировка | — |
| permissions | Guard и декоратор `@RequirePermissions(...)` | users |
| settings | Валюта, параметры, справочники статусов и типов RO App с маппингом | — |
| categories | Категории (тип: товар или расход), активность вместо удаления | — |
| suppliers | Поставщики, активность вместо удаления | — |
| products | Каталог: название, категория, единица, фото, ссылки, активность. Остатков не хранит | categories |
| clients | Клиенты из RO App (кэш, читаются через API) | integration |
| warehouse | Партии, остатки, FIFO-план, корректировки. Единственный источник правды по остаткам | products |
| purchases | Закупки и позиции, отмена; партии создаёт через warehouse | products, suppliers, warehouse, allocations, audit |
| orders | Кэш заявок из RO App, сырой и смапленный статус, признак «закрыта» | clients, settings |
| allocations | Вложения: FIFO-списание, возврат, отмена, перенос, правка закрытой заявки с причиной | warehouse, orders, audit |
| integration-roapp | Клиент RO API (токен только на сервере), вебхук, ручной sync, ночной cron, IntegrationLog | orders, clients, settings |
| audit | Запись журнала (внутри транзакций) и чтение с фильтрами | — |
| reports | Только чтение: дашборд, себестоимость, остатки по стоимости, экспорт | warehouse, allocations, purchases |

Правило разделения: модули, пишущие деньги и остатки (warehouse, purchases, allocations), не пишут в таблицы друг друга напрямую, а вызывают сервисы. Тогда FIFO тестируется отдельно.

«Нераспределённые закупки» отдельного модуля не имеют. Это представление над партиями (`qtyRemaining > 0`), например фильтр или эндпоинт в warehouse/purchases.

## 2. Инварианты (сервер обязан их гарантировать)

1. Остаток не уходит в минус никогда, без исключений. Ручная корректировка тоже не может списать больше, чем есть (проверка под блокировкой партий).
2. Списание только FIFO. Цена вложения равна цене списанной партии и после вложения не меняется.
3. Деньги, остатки и аудит пишутся в одной транзакции. При списании партии блокируются (`SELECT ... FOR UPDATE`), иначе параллельные запросы спишут одну партию дважды.
4. Закупка не равна расходу. Закупка создаёт партии, расход создаёт вложения. Закупка «в заявку» создаёт партию с нулевым остатком и сразу вложение.
5. Нулевой остаток не удаляет товар.
6. Закрытая заявка (только статус «Выдан», локальный `closed`; «Готово» не блокирует): правка вложений только с правом `allocations.edit_closed`, с причиной, с записью в аудит.
7. Перенос и возврат не создают новых расходов.
8. Статус RO App без маппинга сохраняется сырым, заявка не падает, попадает в список «требует маппинга».
9. Синхронизация RO App идемпотентна по внешнему ID. Вебхук, кнопка и cron вызывают одну функцию. Ничего не отправляется обратно в RO App.
10. Права проверяются на сервере на каждом эндпоинте, включая индивидуальные разрешения.
11. Финансовые записи не удаляются: только отмена, возврат, корректировка.
12. Сверка: сумма остатка по всем неотменённым закупкам плюс остаток партий-корректировок (`adjustment`, без закупки) равна сумме стоимости остатков по всем товарам склада (покрыть тестом).

## 3. Решения, которые надо принять до шага 1

- **Формат денег.** Копейки целым числом (как в клиенте) или `Decimal(14,2)`. Рекомендация: копейки целыми, меньше сюрпризов с округлением.
- **Правило отмены закупки.** Выписать условия из `canCancelPurchase` в `calc.ts` явно.
- **Refresh-токен.** Хранить в БД с возможностью отзыва (рекомендация) или только короткий access.
- **Аутентификация вебхука RO App.** Проверить формат подписи или секрета по документации RO App вручную.

## 4. Пошаговый план

0. **Каркас.** Nest-проект, Postgres в Docker, Prisma, ConfigModule с валидацией env, ValidationPipe, префикс `/api/v1`, фильтр ошибок, Swagger, `/health`. *Готово:* `/health` отвечает, миграция применяется на пустой базе.
1. **Схема БД.** Все сущности из ТЗ, индексы под поиск и FIFO (партии по товару и дате), миграция, seed на основе `client/src/mocks/seed.ts`. *Готово:* seed заполняет базу.
2. **Auth, пользователи, права.** Логин, JWT, refresh, хеш паролей (argon2 или bcrypt), guard, базовые наборы прав для админа и исполнителя плюс индивидуальные. *Готово:* без права 403, деактивированный пользователь не проходит.
3. **Справочники.** Категории, поставщики, товары, настройки, маппинги статусов и типов. *Готово:* товар создаётся, деактивируется, фильтруется.
4. **Склад как чистая логика без HTTP.** `planFifo` и расчёт остатка, порт из `calc.ts` с юнит-тестами (нехватка остатка, партии одной цены, нулевые партии). *Готово:* покрыты все ветки.
5. **Закупки.** Создание на склад или в заявку, отмена по правилу, список, карточка, всё в транзакции с аудитом. *Готово:* остаток растёт, закупка в заявку создаёт вложение, отмена откатывает, аудит записан.
6. **Заявки (кэш) и вложения.** Добавление с FIFO под блокировкой, возврат, отмена, перенос, правка закрытой заявки с причиной. *Готово:* тест на два параллельных вложения одной партии без минуса.
7. **Корректировки остатков.** Только с причиной и правом `inventory.manage`. Плюс создаёт партию-корректировку, минус списывает по FIFO и не может превысить остаток.
8. **Аудит.** Сервис записи (из транзакций) и чтение с фильтрами.
9. **Интеграция RO App.** Клиент с Bearer, маппинг, одна функция sync, ручной эндпоинт, приёмник вебхука с проверкой секрета, ночной cron, IntegrationLog. Тест на повтор одного заказа. *Готово:* повторный sync без дублей, неизвестный статус сохраняется сырым, при недоступности API работа на кэше.
10. **Отчёты.** Дашборд, себестоимость по поставщику, сотруднику, типу техники, остатки по стоимости, экспорт XLSX/CSV/PDF. *Готово:* суммы совпадают с вложениями и партиями.
11. **Hardening.** E2E на инварианты, rate limit на логин, idempotency key на создание закупок и вложений, резервное копирование, логи без персональных данных.
12. **Подключение фронта.** Написать `client/src/api/http/` с HTTP-реализацией `ApiClient` (контракт `api/contract/`) и заменить экспорт в `api/active-client.ts`. Страницы и хуки не меняются: они уже работают через контракт и кэш TanStack Query. Добавить пагинацию и серверную сортировку списков.

## 5. Что уходит на сервер, а что остаётся на клиенте

- На сервер: `api/mock/engine/*` (FIFO, склад, закупки, вложения, корректировки, отчёты, права, аудит; часть расчётов станет SQL) вместе с тестами, включая `invariants.test.ts` и `assert-invariants.ts`; `api/mock/seed/*` как seed-скрипт; `api/contract/*` как спецификация эндпоинтов и DTO; обработчики `api/mock/handlers/*` показывают, как собирать ответы (имена, суммы, флаги `locked`).
- Не переносится: `api/mock/engine/integration.ts` (`syncRoApp`). Это симуляция вебхука (случайная заявка через `Math.random()`), на сервере её заменяет настоящий клиент RO App с одной функцией синхронизации (шаг 9).
- На клиенте остаётся: `pages`, `components`, `api/hooks`, `store/ui-store.tsx`, `lib`, роутинг. Заменяется только `api/mock` (на `api/http`).
- Перенос больше не требует правок страниц: прямых обращений UI к базе нет, всё идёт через `ApiClient`.
