# Рефакторинг клиента: слой API и изолированная имитация сервера

Статус: черновик на утверждение. Автор запроса: разработчик. Затрагивает только `client/`, плюс обновление `docs/`.

## 1. Зачем

Сейчас «сервер» размазан по клиенту. Страницы получают через `useDb()` всю базу целиком (`Db`), сами считают из неё нужное функциями из `domain/calc.ts` и пишут через `apply((draft) => операция(draft, …))`. Такой код нельзя подключить к настоящему API без переписывания каждой страницы.

Цель: вся имитация сервера лежит в одной папке. Когда бэкенд будет готов, разработчик пишет реализацию того же контракта поверх HTTP, меняет одну строку, и страницы не трогаются. Дополнительно: максимально подробные комментарии и разбивка больших файлов на небольшие.

## 2. Цели, не-цели, анти-цели

**Цели**
- Страницы и компоненты не знают про `Db`, `localStorage`, FIFO и аудит. Они вызывают только контракт (`src/api`).
- Контракт повторяет будущий REST: модули из `docs/03-backend-plan.md`, ответы с уже посчитанными полями (как отдаст сервер).
- Имитация (`src/api/mock/`) целиком заменяема. Бизнес-логика в ней остаётся почти без изменений, чтобы потом переехать в NestJS.
- Поведение приложения для пользователя не меняется, кроме мелких состояний загрузки.
- Подробные комментарии, файлы не длиннее примерно 250–300 строк.

**Не-цели**
- Не пишем HTTP-клиент и не трогаем `server/`.
- Не переделываем мобильный дизайн (по `CLAUDE.md`), не меняем внешний вид.
- Не добавляем пагинацию и серверную сортировку (см. раздел 7).
- Не меняем бизнес-правила.

**Анти-цели (провал, даже если всё работает)**
- Страница, которая всё ещё читает целую базу или импортирует что-то из `api/mock/`.
- Логика расчёта денег или остатков, продублированная в UI и в имитации.
- Контракт, придуманный под текущий UI и непохожий на то, что сможет отдать сервер.

## 3. Подходы (выбран первый)

1. **Слой API между страницами и сервером** (выбрано разработчиком). `src/api/` содержит контракт и хуки, `src/api/mock/` содержит имитацию. Плюс: замена сервера заменой одной папки, это шаг 12 плана. Минус: переписываем чтение данных на всех страницах, появляются состояния загрузки.
2. Только вынос в `mock-server/` без смены чтения страниц. Дешевле, но заменить папку без переписывания страниц нельзя. Отклонено.

## 4. Структура

```
client/src/
  api/
    index.ts              единственная точка входа: экспорт api и хуков
    contract/             то, что видят страницы (типы + интерфейс)
      types.ts            DTO, входные данные, общие enum (бывший domain/types.ts)
      client.ts           интерфейс ApiClient по модулям
      result.ts           ApiResult<T> (бывший OpResult)
    hooks/                тонкая обёртка над ApiClient для React
      use-*.ts            запросы (чтение) и мутации (запись) по модулям
    mock/                 ВСЯ имитация сервера, заменяется целиком
      index.ts            создаёт ApiClient поверх mock-хранилища
      storage.ts          хранилище в localStorage, загрузка и сброс демо-данных
      latency.ts          имитация задержки сети
      engine/             бизнес-логика (бывшие domain/ops.ts, domain/calc.ts)
        fifo.ts, stock.ts, purchases.ts, allocations.ts,
        catalog.ts, users.ts, audit.ts, integration.ts,
        reports.ts, permissions.ts, money.ts
      handlers/           реализация ApiClient по модулям (вызывает engine)
      seed/               демо-данные (бывший mocks/seed.ts, разбит по сущностям)
  lib/                    остаётся: format, utils; сюда же уходят UI-подписи (labels)
  store/ui-store.tsx      остаётся (тема, мобильный режим, тосты)
  components, pages       только контракт и хуки
```

Правило зависимостей: страницы и компоненты импортируют только `@/api` (публичный `index.ts`). Из `@/api/mock/*` не импортирует никто, кроме `api/index.ts`. Это проверяется правилом ESLint (`no-restricted-imports`).

## 5. Контракт (по модулям `03-backend-plan.md`)

Все методы асинхронные и возвращают `Promise`. Бизнес-ошибки (нет остатка, нет причины, нет права) приходят как `ApiResult` с `ok: false` и текстом, как сейчас `OpResult`. Сервер потом отдаёт то же через 4xx, HTTP-клиент приведёт к этому виду.

| Модуль | Чтение | Запись |
|---|---|---|
| auth | `me()` (пользователь + `permissions[]`), `listDemoUsers()` | `login`, `logout` |
| users | `list()` | `create`, `update` |
| categories | `list()` | `create`, `update` |
| suppliers | `list()` (с суммой закупок) | `create`, `update` |
| products / warehouse | `listStock()` (товар + остаток, цена, стоимость), `getProduct(id)` (партии), `previewFifo(productId, qty)`, `stockTotals()` | `createProduct`, `updateProduct`, `adjustStock` |
| purchases | `list()`, `get(id)` (с позициями, партиями, `status`, `totalKop`, `allocatedKop`, `remainingKop`, `canCancel`) | `create`, `cancel` |
| orders | `list(filters)` (с `costKop`, `lastOperationAt`), `get(id)` (вложения, история, разбивка по категориям, `statusLabel`, `locked`) | — (только RO App) |
| allocations | — | `add`, `release`, `transfer` |
| reports | `dashboard(range)`, `analytics(filters)` | — |
| audit | `list(range, filters)` | — |
| integration | `status()`, `syncLog()` | `sync(source)` |
| settings | `get()` | `update(patch)` |

Поля, которые раньше считал UI (`purchaseTotalKop`, `purchaseStatus`, `orderCostKop`, `isOrderLocked`, подпись статуса через справочник), теперь приходят уже готовыми в DTO. Благодаря этому страница не нуждается ни в `Db`, ни в `calc.ts`.

В клиенте остаются только чисто UI-вещи: форматирование (`lib/format`), подписи enum (`labels`), выбор периода (`PeriodKey`, `rangeFor` формирует запрос), `can(permission)` по списку прав из `me()`. Решение о доступе на самом деле принимает сервер, UI лишь прячет кнопки.

## 6. Хуки и данные

Чтение и запись идут через TanStack Query (`@tanstack/react-query`). После мутации инвалидируются связанные ключи (закупка меняет остатки, закупки, дашборд, журнал). Страницы получают `{ data, isLoading, error }`. Для списков показывается `Skeleton` (компонент уже есть).

Хуки лежат по модулям (`use-purchases.ts` и т. д.) и не содержат бизнес-логики: вызов `api.<модуль>.<метод>` плюс ключи кэша.

## 7. Принятые решения (мои, разработчик может изменить)

- **TanStack Query** как слой кэша. Это стандартный выбор для будущего API, его же будет использовать настоящий клиент. Добавляется зависимость `@tanstack/react-query` (нужно ваше «да» на установку).
- **Задержка сети в имитации** по умолчанию 150 мс, настраивается переменной `VITE_MOCK_LATENCY_MS`. Нужна, чтобы сразу видеть пропущенные состояния загрузки, а не находить их после подключения сервера.
- **Списки возвращаются целиком**, но методы принимают параметры фильтра, которые потом будут серверными. Пагинацию и серверную сортировку добавим на шаге подключения настоящего API.
- **Язык комментариев**: в `api/mock/engine` (это бывший `domain/`, логика уедет на сервер) комментарии на украинском, как правило проекта для `domain/`. В остальном коде комментарии на английском. Идентификаторы везде английские. Тексты интерфейса на украинском.
- **Постоянство данных**: `localStorage`-ключ остаётся `mlt-oblik:db:v1`, чтобы не терять демо-базу. Формат базы внутри имитации не меняется.
- **Миграция по шагам**: приложение собирается и работает после каждого шага, страница переводится на контракт целиком или не трогается.
- **`syncRoApp`** остаётся в `mock/engine/integration.ts` как симуляция и на сервер не переносится (по `03-backend-plan.md`, раздел 5).

## 8. Порядок работы (укрупнённо; подробный план делает `writing-plans`)

1. Каркас: `api/contract`, `api/mock` (хранилище, latency), `api/index.ts`, `QueryClientProvider`, правило ESLint.
2. Перенос `domain/` в `mock/engine` с разбивкой по файлам и комментариями, вынос `seed` по сущностям.
3. Модули по одному (справочники и пользователи, склад, закупки, заявки и вложения, отчёты, журнал, интеграция, настройки): handlers + хуки + перевод страниц.
4. Разбивка больших страниц и диалогов на меньшие компоненты и функции.
5. Удаление `domain/`, `store/db-store.tsx`, `mocks/`. Обновление `CLAUDE.md`, `client/README.md`, `docs/04-frontend-status.md`.

После каждого шага: `npm run build` (`tsc -b`) и `npm run lint`. Автотестов в клиенте нет. Проверка поведения идёт вручную по демо-сценариям (закупка, вложение, возврат, перенос, закрытая заявка, корректировка, отмена закупки).

## 9. Оставлено исполнителю

Точные имена DTO и полей, разбиение engine по файлам, имена хуков, детали ключей кэша, разбиение конкретных страниц на компоненты.
